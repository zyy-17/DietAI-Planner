一、现有模块分析

1.1 系统架构

项目采用三层架构，食谱模块跨全部三层：

层技术栈食谱模块职责
前端展示层Vue3 + Element Plus + ViteMealPlan.vue（我的食谱/广场）、RecipeSheet.vue（食谱编辑器）、FoodLibrary.vue（自定义食物）
业务逻辑层Spring Boot (8080)MealPlanService（1757行，核心编排）、MealPlanController（REST API）、FoodController
AI 服务层FastAPI (8000)meal_plan_service.py（目前仅实现 replace 替换）、llm_service.py（LLM 调用封装）

1.3 现有 AI 能力

当前 ai-service 仅有一个食谱相关端点：

POST /api/meal-plan/replace
→ 输入：被替换食物 + 候选列表 + 用户偏好
→ 输出：{ recommendations: [{ food, amount, reason }] }
→ 对应 Java 方法：MealPlanService.getAlternatives()

已实现可用 此能力在 RecipeSheet 编辑器中通过「换一个」按钮触发。

1.4 已删除的能力

POST /api/meal-plan/generate（AI 一键生成完整食谱）已删除——原实现因输出质量不稳定、token 消耗大等原因被移除。本方案将重新设计并实现此功能。

二、AI 应用场景总览

基于对现有模块的全面分析，设计 三个 AI 应用场景，覆盖食谱的「创建 → 编辑 → 审阅」全生命周期：

场景一 AI 智能生成

用户输入想法 → AI 生成完整 N 天膳食计划 → 写入食谱 → 进入编辑器

生命周期阶段：创建

场景二 AI 智能替换

用户不想吃某食物 → AI 从候选中推荐替代品 → 用户选择替换

生命周期阶段：编辑（已实现）

场景三 AI 智能营养分析

用户查看已创建/已执行的食谱 → AI 分析营养结构 + 给出改进建议 → 展示报告

生命周期阶段：审阅/复盘

三、场景一：AI 智能生成食谱（核心新增）

3.1 功能定位

这是本方案的核心新增功能——让用户通过自然语言描述自己的饮食需求，AI 自动生成一份结构化的多天膳食计划，直接写入数据库并在编辑器中打开供用户调整。

3.2 触发入口

在 MealPlan.vue 的「新建食谱」弹窗中，新增一个 Tab 切换：

手动创建（原有）

选目标 → 选周期 → 逐天逐餐手动添加食物

✨ AI 智能生成（新增）

描述想法 → AI 一键生成完整计划 → 进编辑器微调

3.6 Prompt 设计要点

  1. 角色设定：你是一位专业的注册营养师，擅长根据用户需求制定科学膳食计划
  2. 食物白名单约束：将系统食物库 + 用户自定义食物列表注入 prompt，要求 AI 只从列表中选择食物，不得编造列表外的食物名
  3. 严格 JSON 输出格式：强制输出上述结构化 JSON，方便程序解析
  4. 营养约束：若用户给了每日热量目标，要求 AI 控制每天总热量在目标 ±10% 以内
  5. 多样性要求：不同天数之间要有变化，不要完全重复
  6. 思维链控制：明确提示"不要在思考过程中反复核算营养值，直接给出搭配方案"（避免 max_tokens 被思考占满导致截断）
  7. max_tokens 设置：3 天计划设 4096，7 天计划设 8192

3.7 Java 后端处理逻辑（关键步骤）

  1. 创建空 MealPlan：复用现有 create() 方法，status=idle, publishStatus=none
  2. 组装食物库白名单：查询 food 表 + user_custom_food 表，精简为 {name, calories, protein, carb, fat} 列表，发给 ai-service
  3. 调用 ai-service：复用现有 callAiService("/api/meal-plan/generate", body) 方法
  4. 解析返回 JSON：校验结构合法性（days 数组长度=周期、每天的 meals 包含选定餐次）
  5. 食物名 → foodId 匹配：复用现有 FoodPool.match(foodName) 模糊匹配
    • 匹配成功 → foodSource=system/user，foodId=匹配到的ID，营养值按 food 表换算
    • 匹配失败 → foodSource=ai，foodId=null，营养值取 AI 估算值（如果 AI 返回了的话），否则跳过该条目并记录 warning
  6. 批量写入 MealPlanItem：复用现有的 item 新增逻辑，计算 sortOrder
  7. 记录生成日志：复用 writeGenerationLog() 写入 ai_generation_log 表
  8. 返回 planId：前端拿到后调用 openSheet(planId, 'mine') 打开编辑器

四、场景二：AI 智能替换食物（已有能力）

4.1 当前实现状态

✅ 已实现并上线 这是目前食谱模块唯一已实现的 AI 功能。

4.2 功能说明

用户在 RecipeSheet 编辑器中查看某条食物时，点击「换一个/AI 替换」按钮：

  1. 前端收集当前食物信息（名称、克数）、用户不想吃的原因（可选填）、候选食物列表（从食物库中按热量接近度预筛选）
  2. Java 调用 GET /{planId}/item/{itemId}/alternatives → 内部调 ai-service POST /api/meal-plan/replace
  3. AI 返回 3-4 个替代建议（每个含食物名、推荐克数、推荐理由）
  4. 前端以卡片形式展示，用户点击即替换原食物

4.3 技术细节

项值
ai-service 端点POST /api/meal-plan/replace
Prompt 模板FOOD_REPLACE_PROMPT（system_prompt.py）
重试策略最多 3 次，前 2 次强制 json mode，第 3 次放开
max_tokens4096
降级策略AI 调用失败时，退化为按热量接近度排序的纯算法推荐
Java 侧方法MealPlanService.getAlternatives(planId, itemId, reason)

4.4 本方案中的优化点

  • 无需大改，当前实现已经比较完善
  • 可考虑增加：替换时自动同步更新当天营养汇总（已有此逻辑，确认闭环即可）
  • 可考虑增加：记录用户的替换偏好（如经常替换掉某类食物），用于优化未来生成质量

五、场景三：AI 智能营养分析（新增）

5.1 功能定位

对已创建或已执行过的食谱进行 AI 驱动的营养分析，生成人类可读的分析报告。这不是简单的数值汇总（前端已有饼图/柱图），而是 AI 基于营养学知识给出的解读性建议。

5.2 触发入口

两个位置：

  1. RecipeSheet 编辑器内：顶部工具栏新增「AI 分析」按钮，点击后在侧边面板展示分析结果
  2. 我的食谱卡片上：卡片操作区新增「AI 诊断」入口，点击弹出分析报告弹窗

5.3 输入数据

数据项来源说明
食谱基本信息meal_plan 表名称、目标、周期、每日餐次
完整食物清单meal_plan_item 表每天每餐的所有食物条目（名称、克数、营养快照）
营养汇总前端/Java 聚合计算每天/全局的总热量、蛋白质、碳水、脂肪
宏量营养素比例前端计算碳水% / 蛋白质% / 脂肪%
执行记录（如有）diet_record 表用户实际打卡情况，用于对比「计划 vs 实际」
用户目标meal_plan.goal减脂/增重/维持，影响分析角度

5.4 输出内容设计

{ "summary": "这份3天减脂食谱整体设计合理，日均约1480kcal...", "daily_analysis": [ { "day": 1, "total_calories": 1512, "macro_ratio": { "carb_pct": 45, "protein_pct": 30, "fat_pct": 25 }, "evaluation": "蛋白质占比优秀，符合减脂期需求", "suggestions": ["晚餐可适当减少碳水占比"] }, ... ], "overall_suggestions": [ "蔬菜种类偏少，建议增加深色蔬菜摄入", "第3天晚餐热量偏高，可调整为主食减半", "整体缺乏优质脂肪来源（坚果、牛油果），建议每日添加一小份" ], "nutrition_score": 82, // 百分制评分 "risk_warnings": [ "钙摄入量可能不足，建议补充乳制品或绿叶菜" ] }

5.6 与现有模块的关系

此功能是纯只读分析，不修改任何 meal_plan 或 meal_plan_item 数据。它读取已有的食谱数据，交给 AI 做语义层面的分析和建议输出。可以理解为给现有的营养可视化（饼图/柱图）加上一层AI 解读。

六、数据流与核心原则

三大核心原则（贯穿所有 AI 场景）

原则说明适用场景
原则一：AI 不管算数 AI 只负责输出「食物名称 + 克数」，所有营养值（calories/protein/carbohydrate/fat）一律由 Java 后端根据 food 表的 per-100g 值按克数换算。绝不使用 AI 返回的营养数据作为权威值。 场景一、场景二
原则二：食物来源三态 MealPlanItem.foodSource 严格区分三种来源：
• system — 匹配到系统食物库
• user — 匹配到用户自定义食物
• ai — 食物库中无此食物，AI 编造的（foodId=null）		 场景一（主要）、场景二
原则三：生成即初稿 AI 生成的食谱不是最终产品，而是「智能初稿」。生成完成后自动进入 RecipeSheet 编辑器，用户必须能够查看、修改、删除任何一条 AI 生成的食物条目，确认无误后再发布。 场景一

7.3 风险与应对

风险影响应对措施
AI 输出食物名在 food 表中找不到场景一：部分食物无法入库Fuzzy match（模糊匹配）；仍匹配不到则标记为 SOURCE_AI 并用 AI 自估营养值；记录警告日志
7天计划输出太长被截断场景一：JSON 不完整，解析失败max_tokens 设 8192；Prompt 明确禁止反复核算；检测到截断异常后直接报错提示用户缩短周期
AI 不遵守 JSON 格式场景一、三：解析失败复用 _clean_json() 清洗；前 2 次重试强制 json mode；第 3 次放开并用正则抽取
AI 生成质量不满意用户体验差"生成即初稿"原则——生成完进编辑器，用户可任意修改；提供「重新生成」按钮
API 费用（长输出 = 更多 token）成本前端生成前显示预估 token 消耗提示；7天计划的 max_tokens 更高但用户可自主选择 3 天降低成本
ai-service 未启动功能不可用Java 侧 catch 异常后返回友好提示"AI 服务未响应"；场景二已有此降级（退化为算法排序）

八、方案价值总结

对课程作业的价值

  1. 体现AI 工程化落地能力：不是简单调 API，而是设计了完整的「前端→后端→AI服务→LLM」多层协作链路
  2. 展现软件工程思维：需求分析→场景设计→API 设计→数据流→风险管控，形成完整闭环
  3. 贴合竞赛主题：「大数据与人工智能应用」——AI 膳食规划是典型的 AI 垂直领域应用
  4. 技术栈完整性：Vue3 + Spring Boot + FastAPI + LLM，覆盖前后端 + AI 服务

对产品体验的价值

  1. 降低使用门槛：用户不需要懂营养学，用自然语言描述需求即可获得专业食谱
  2. 提升编辑效率：AI 生成初稿 + 人工微调，比从零手动添加效率提升 10 倍以上
  3. 增强专业性：AI 营养分析提供超越数值汇总的深度解读和建议
  4. 完整覆盖生命周期：创建（生成）→ 编辑（替换）→ 复盘（分析），三个环节都有 AI 加持
